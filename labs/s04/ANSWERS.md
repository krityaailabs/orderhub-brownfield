# Section 4: reference answers

## 4.1 Who owns which tests?

| Test type | Who should own it with agents |
|---|---|
| Acceptance tests (from the spec's criteria) | The team, written or approved by a human **before** the code; agents must not edit them |
| Unit tests for new code | The agent may propose them; a human reviews them like code |
| Property-based tests for rules (money, invariants) | A human states the property; the agent may write the generator |
| Characterisation tests (legacy behaviour) | Generated by tooling or an agent, reviewed for coverage; regenerated only on an intended change |
| Contract tests (handoff, APIs other teams use) | The owners of the contract, often with the other team |

## 4.4 Incident: the agent edited the test

- **Hypothesis:** the implementation is wrong and the test was changed to match it.
- **Evidence:** the PR summary says "updated one test whose expected value was inconsistent"; the diff changes AC-2's expected value from 4095 to 4500; the session notes show three failed attempts before editing the test; the formula divides by the total instead of the subtotal and then divides the share by ten.
- **Root cause:** "done when the tests pass" was the stop condition, and test files were editable without review.
- **Mitigation:** revert the PR; recompute affected refunds; tell finance.
- **Permanent fix:** acceptance tests are protected (`make protect-tests` in CI as a required check; a hook in Section 5); AGENTS.md boundary already says never edit an existing test; reviewers read test diffs first.
- **Detection signal:** any PR that changes lines in existing test files without `[test-change-approved]`.
- **Context update:** add to the slice request "if a test looks wrong, stop and explain; do not edit it".

## 4.6 Surviving mutants (with acceptance and property tests only)

| Mutant | Why it survives | A test that kills it |
|---|---|---|
| rounding: half-up becomes floor | Every share in the spec's examples has a fractional part below .5 (455.0, 37.3, 187.4) | A share with a fraction of .5 or more: the pen in NB-A5 + PEN with STAFF30 has share 74.7 → refund 174 |
| window boundary: >= becomes > | Tests use 30 days plus a second, and 29 days 23 hours; nothing tests exactly 30 days | Call `return_items` with `now = created_at + 30 days` and expect "return window closed" |

The property tests don't kill the rounding mutant because the remainder rule hides small allocation errors in the final refund. That's a lesson in itself: an invariant on the sum can't see how the sum is split.

## 4.7 What the golden master proves

It proves the discount function gives the same results as when the golden file was recorded, for 170 input pairs. It doesn't prove those results are right. If the function had a bug when the file was recorded, the golden master protects the bug. Use it to make refactors safe, and use the spec and ADR 0001 to decide what's right.
